# Уведомления об ограничениях пользователей

Алерт-бот отправляет события в маршрут, выбранный в **Админушка → Алерты**: один топик группы либо личные чаты главного администратора и отмеченных операторов. Старые `ALERT_CHAT_ID` и `ALERT_THREAD_ID` монитора служат только начальной конфигурацией до перехода на интерфейс. [Подключение и переключение маршрута](MANAGER_BOT_SETUP_RU.md#алерт-бот).

## Что приходит

- Назначена капча, попытка не прошла, капча пройдена, срок проверки закончился или проверка отменена.
- Антиспам временно ограничил пользователя; срок закончился или ограничение сняли вручную.
- Оператор ограничил, заблокировал или разблокировал пользователя.
- Сообщение остановлено лимитом частоты, очередь капчи заполнена или проверка антиспама недоступна.

В уведомлении указаны бот, пользователь, Telegram ID, время события, срок ограничения и текущее состояние. Если тема существует, есть ссылка на неё. Если темы ещё нет, найдите пользователя через **Админушка → Поиск** по Telegram ID. Имя берётся из темы или сохранённой очереди; когда этих данных нет, остаётся точный ID.

Алерты не копируют текст личной переписки. В них может быть внутренняя причина блокировки, заданная оператором. Управление доступом остаётся в обычных карточках поддержки; уведомление само никого не разблокирует.

**Пройденная капча не означает, что сообщения уже доставлены.** Уведомление показывает количество ожидающих сообщений в очереди капчи. Сообщения, остановленные лимитом, ручным ограничением или блокировкой, могут не сохраняться: после снятия ограничения нужно попросить пользователя повторить их.

## Когда и как отправляются

После принятого обновления Telegram и результата проверки запускается фоновая отправка. Повторная обработка того же обновления не создаёт новое событие. До трёх событий объединяются в одно сообщение; при накоплении очереди уведомления могут прийти позже. События показывают своё время и состояние пользователя на момент подготовки уведомления.

Срабатывания лимита и заполнения очереди группируются по пользователю, боту, причине и пятиминутному окну. В пределах окна приходит не более одного такого алерта; количество в нём отражает срабатывания, накопленные к моменту подготовки отправки. Обычные доставленные сообщения алертов не создают.

Фоновые задачи основного Worker каждые 5 минут и монитора каждые 15 минут повторяют работу с очередью, включая истечение сроков. Они используют общий запрет параллельной отправки. При явном отказе Telegram уведомление остаётся для повторной попытки, с учётом `retry_after`.

При неопределённом результате отправки (например, Telegram принял сообщение, но соединение оборвалось до ответа) автоматический повтор подавляется. Событие сохраняется с отметкой `uncertain_at`, а в логах появляется `user_access_alert_send_failed` с `uncertain: true`. Если процесс оборвался после отметки начала запроса, следующий запуск также сохранит неопределённый результат. Успешную отправку в таком случае гарантировать нельзя.

Подтверждённые и неопределённые события очищаются порциями после 30 дней. Ожидающие события сохраняются до обработки. Полная очистка истории удаляет эту очередь и отменяет отправку ещё не начатых старых пакетов. Срок проверяется перед уведомлением, чтобы продление не выглядело как снятие ограничения. Если срок закончился, но есть другая блокировка, она указана в строке «Сейчас».

## Обновление работающей установки

Этот раздел сохраняет шаги исторического выпуска 0028. При установке текущего кода следуйте [руководству первого запуска](DEPLOY_FIRST_TIME_RU.md) или [обновления существующих баз](DATABASE_SETUP.md), затем подключите алерт-бота через Админушку.

Если в базе уже установлены 0026 и 0027, для этого обновления нужна только **0028_user_access_alerts.sql**. Уже установленные миграции пропускаются. Миграций монитора и новых секретов нет. Новое подключение `USER_ACCESS_ALERTS` уже добавлено в основной `wrangler.toml`.

1. Сохраните свежую резервную копию:

   ```powershell
   $accessBackupDir = Join-Path $env:USERPROFILE '.codex\backups\telegram-support'
   New-Item -ItemType Directory -Path $accessBackupDir -Force | Out-Null
   $accessBackup = Join-Path $accessBackupDir ('before-access-alerts-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.sql')
   npx.cmd --yes wrangler@4.128.0 d1 export telegram-support --remote --config wrangler.toml --output "$accessBackup"
   if ($LASTEXITCODE -ne 0) { throw 'Экспорт не завершён. Следующий шаг пока не выполняйте.' }
   ```

2. Примените миграцию:

   ```powershell
   npx.cmd --yes wrangler@4.128.0 d1 migrations apply telegram-support --remote --config wrangler.toml
   if ($LASTEXITCODE -ne 0) { throw 'Миграция не завершена. Публикацию пока не выполняйте.' }
   ```

   Дождитесь ✅ у 0028. Если предыдущие миграции ещё не установлены, эта же команда применит их по порядку. Существующая переписка сохраняется. Уже активные ограничения и ожидающие капчи попадут в новую очередь; старые успешные проверки не рассылаются.

3. Сначала опубликуйте **монитор**, который теперь умеет отправлять новые уведомления:

   ```powershell
   npx.cmd --yes wrangler@4.128.0 deploy --config monitor/wrangler.toml
   if ($LASTEXITCODE -ne 0) { throw 'Монитор не опубликован. Основной Worker пока не публикуйте.' }
   ```

4. Опубликуйте основной Worker:

   ```powershell
   npx.cmd --yes wrangler@4.128.0 deploy --config wrangler.toml
   ```

5. Проверьте событие на своём тестовом аккаунте: ограничьте его через карточку пользователя, затем снимите ограничение. Обе записи должны появиться в выбранном маршруте алертов — топике группы или личке. Для капчи используйте обычную проверку, не массовую отправку сообщений. Если уведомления не появились сразу, дайте фоновому запуску обработать очередь и проверьте логи `user_access_alerts_deferred` / `user_access_alert_send_failed`.

Для первой установки с нуля следуйте [основному руководству](DEPLOY_FIRST_TIME_RU.md): сначала основной Worker без обеих связей с монитором, затем монитор, затем основной Worker с обеими связями.

## Проверки разработки

- `node --test test/user-access-alerts.test.js` — события, группировка, одновременные отправки, 429, потерянный ответ, очистка и обновление схемы.
- `npm.cmd test` — полный набор, включая обработчики Free, капчу, ручную доставку, ограничения и блокировки.
- `node scripts/validate-wrangler.mjs` — сборка обоих Worker.
- Дополнительно проверена локальная связка двух Worker в workerd: HTTP-прохождение капчи → события D1 → `waitUntil` → RPC монитора → одна отправка алерт-ботом в топик 3 → сохранение подтверждения.
