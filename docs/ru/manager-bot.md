# Управляющий бот поддержки: установка и проверка

Управляющий бот — отдельный бот Telegram. Он показывает меню в General и личные рабочие экраны операторов, проверяет группы и отправляет адресные уведомления. Сообщения клиентов по-прежнему доставляют сервисные боты. Отдельный алерт-бот подключается и настраивается через меню **Алерты** в личке управляющего бота.

## Обновление работающей установки

Миграции основной базы до `0056` и мониторинга до `0007` добавляют [статистику поддержки и расписания отчётов](reports.md). Для этой функции обновите оба Worker; новые секреты не нужны.

Миграция `0054_manager_home_screens.sql` добавляет общий для повторных команд адрес личного меню. Несколько `/start`, `/menu`, `/groups` или открытий по ссылке `start=menu`, полученных в пределах 10 секунд, обновляют одно меню. Следующая команда после этого интервала либо перехода в другой раздел создаёт новое меню. Параллельные открытия защищены арендой, отправки с неясным исходом автоматически не дублируются. Состояние ограничено одной строкой на оператора, удаляется при полном сбросе и очищается после семи дней неактивности.

Событие `manager_update_timing` в логах показывает `source_age_ms` (возраст команды при поступлении webhook), `elapsed_ms` (время внутри обработчика), число D1-запросов и класс ошибки; для ошибок отправки меню — код Telegram и `retry_after_seconds`. Тексты сообщений, имена и токены в это событие не записываются.

1. Проверьте миграции на изолированной локальной D1 командой `node scripts/validate-d1-migrations.mjs`. Перед обновлением сохраните экспорт рабочей D1 по [инструкции обновления](database-upgrade.md). Если экспорт не удался, проверьте доступность базы и получите текущую точку [Cloudflare Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) командой `npx.cmd --yes wrangler@4.128.0 d1 time-travel info telegram-support --config wrangler.toml --json`; сохраните её вне Git. На бесплатном плане точка восстановления доступна ограниченное время и откат к ней удалит сообщения, пришедшие после неё. Если не удалось получить ни экспорт, ни точку восстановления, миграции не начинайте. Затем примените все недостающие миграции (сейчас до `0053`) командой `npx.cmd --yes wrangler@4.128.0 d1 migrations apply telegram-support --remote --config wrangler.toml`. Не удаляйте существующую базу и темы.
2. Через [@BotFather](https://t.me/BotFather) создайте отдельного управляющего бота. Сохраните токен в менеджере паролей. При необходимости включите ему **Bot Management Mode** для создания сервисных ботов прямо из Telegram. Для подключения по токену этот режим не нужен.
3. В `wrangler.toml` в блоке `[vars]` проверьте, что `MANAGER_BOT_USERNAME` совпадает с публичным username управляющего бота без `@`. Токен и секрет webhook в файл не записывайте.
4. Сохраните токен через интерактивную команду `npx.cmd --yes wrangler@4.128.0 secret put MANAGER_BOT_TOKEN --config wrangler.toml`: Wrangler скрыто запросит значение. `MANAGER_WEBHOOK_SECRET` — **другой** секрет, его BotFather не выдаёт. Сгенерируйте случайную строку командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`, сохраните её в менеджере паролей и введите через `npx.cmd --yes wrangler@4.128.0 secret put MANAGER_WEBHOOK_SECRET --config wrangler.toml`. Та же строка понадобится при регистрации webhook на следующем шаге. Ни токен, ни секрет не отправляйте в чат и не записывайте в репозиторий. Если ранее не настроен `BOT_REGISTRY_KEY`, сначала выполните [его однократную настройку](bot-registration.md).
5. Выполните локальные проверки `npm.cmd test` и `node scripts/validate-wrangler.mjs`, затем опубликуйте основной Worker по обычной процедуре. После публикации запустите `node scripts/telegram-webhook.mjs manager`: скрипт скрыто запросит токен и секрет, проверит личность бота и текущий webhook, установит `/tg/manager` без очистки ожидающих обновлений.
6. Откройте личный чат управляющего бота и отправьте `/start`. Каждый оператор тоже должен открыть этот чат и отправить `/start`, иначе Telegram может не разрешить личные уведомления.

После первого запуска личный интерфейс Админушки открывается на английском. Каждый оператор может выбрать **🌐 Язык интерфейса** в её главном меню: English, Русский, Español или 简体中文. Выбор действует только для его личного интерфейса. Для клиентов язык задаёт главный администратор отдельно в **Управление ботами поддержки → сервис → ⚙️ Настройки сервиса → 🌐 Сменить язык**; новые сервисы начинают с английского. Сохранённые вручную тексты приветствия и автоответа остаются авторским содержимым и при смене языка сервиса автоматически не переводятся.

Названия кнопок ниже приведены для русского интерфейса. Если после первого запуска видите английские подписи, сначала выберите **🌐 Interface language → 🇷🇺 Русский** или следуйте соответствующим английским кнопкам.

Добавьте управляющего бота администратором в текущую группу и каждую будущую группу с темами. Ему нужны отправка и закрепление сообщений, а также управление темами для закрытия обращений. Сервисному боту нужны отправка сообщений и управление темами для создания тем и доставки ответов. Алерт-бота добавляйте только в ту группу, чей топик выбран для технических предупреждений; для личного режима добавлять его в группу не требуется.

## Алерт-бот

После миграции монитора `0006_alert_delivery_config.sql` один раз установите ключ шифрования командой `powershell.exe -NoProfile -File scripts/initialize-alert-config-key.ps1`. Скрипт не печатает ключ, хранит локальную резервную копию с защитой Windows DPAPI и не заменяет уже установленный ключ. Для восстановления зашифрованного токена вместе с резервной копией D1 нужен тот же ключ. Затем опубликуйте монитор с entrypoint `AlertSettings`, а основной Worker — с binding `ALERT_SETTINGS`. Прежние `ALERT_BOT_TOKEN`, `ALERT_CHAT_ID` и `ALERT_THREAD_ID` продолжают работать, пока маршрут не изменён в интерфейсе. Параметр `ALERT_CONFIG_REQUIRED` не даёт вернуться к прежнему маршруту при потере ключа: доставка в этом случае останавливается.

Только главный администратор открывает **Алерты** в личке управляющего бота. Здесь можно подключить или заменить отдельного алерт-бота токеном из BotFather, выбрать один топик подключённой группы или личные чаты администратора и отмеченных операторов, а также отключить бота. Токен отправляется только в личке и удаляется по возможности; он хранится зашифрованным в D1 монитора. Для первого подключения без прежнего маршрута сначала нажмите Start в личке алерт-бота: первоначальный адрес — личка главного администратора. Алерт-боту webhook не нужен, он только отправляет сообщения.

Для группового режима добавьте алерт-бота в нужную группу с правом писать сообщения, выберите **Переключить в топик группы** и отправьте указанную Админушкой команду `/alerts@имя_управляющего_бота` от своего имени внутри нужного топика. Для личного режима каждый отмеченный оператор должен открыть личку алерт-бота и нажать Start. Перед переключением бот проверяет доставку в каждую новую личку либо в новый топик; если проверка не прошла, прежний маршрут остаётся активным. После сохранения нового маршрута бот сообщает в прежний чат, что алерты туда больше не поступают. Если прежний чат недоступен, Админушка прямо сообщает, что уведомить его не удалось. Обычные предупреждения идут только в один режим: в группе — в один топик, в личном режиме — администратору и отмеченным операторам. Неудача отправки одному оператору после успешной доставки администратору записывается в лог и не дублирует предупреждение администратору.

**Отключить алерт-бота** означает убрать его из нашей системы, а не удалить в BotFather. После отключения монитор продолжает проверки, но технические предупреждения и события доступа не доставляются до нового подключения. Старые значения Wrangler остаются только как резервный маршрут для установки, которая ещё не перешла на управление через интерфейс; отключение через интерфейс не возвращает их обратно.

После включения управляющего бота сервисные боты не показывают списки команд в группе и не публикуют собственное меню. Старая адресованная команда или кнопка управления показывает путь к управляющему боту. В теме оператор закрывает обращение командой `/close` через управляющего бота или кнопкой **Закрыть тему** в его карточке; управляющий бот определяет сервис по теме. Сервисный бот продолжает принимать и доставлять сообщения клиента. Главный администратор открывает **Хранилище** в личке управляющего бота и выбирает группу для тем и ручных заданий; `/storage` в группах больше не используется. Размер баз, правила хранения, техническая очистка и полный сброс относятся ко всей системе. Полный сброс требует отдельного подтверждения в той же личке.

## Подключение сервиса и группы

- В личке управляющего бота администратор открывает **Управление ботами поддержки → сервис → Подключить группу**. Бот выдаёт одноразовую команду `/connect …`; отправьте её в General нужной группы со своего личного аккаунта. ID группы копировать не нужно.
- Если Telegram не подтвердил создание меню, проверьте General. Когда сообщение меню видно, ответьте на него командой `/adoptmenu` от имени главного администратора: бот закрепит найденное сообщение без повторной публикации. Если сообщения точно нет, отправьте `/retrymenu` в General и повторите действие в личке. При ошибке закрепления повторите действие после восстановления права закреплять; уже созданное меню будет использовано повторно.
- Команда `/menu` в General проверяет сохранённый закреп. Если сообщение открепили, бот закрепит его снова; если его удалили, создаст одно новое меню. При неопределённой отправке или прерванной попытке сначала проверьте General и используйте `/adoptmenu` либо `/retrymenu`.
- Мастер проверяет группу с темами, обоих ботов, права и webhook сервисного бота. Перед сменой маршрута он закрепляет меню новой группы, но показывает в нём только уже подключённые сервисы. После смены маршрута добавляет сервис в меню новой группы и убирает его из меню прежней. Если обновление одного из меню не удалось, сервис уже работает в новой группе: откройте `/start` в личке, нажмите **Продолжить подключение группы** и завершите обновление. Старую историю мастер оставляет на месте. При ответе или нажатии старой кнопки сервисный бот открывает актуальную тему и даёт на неё ссылку; текст из старой темы клиенту не отправляется, его нужно повторить в новой.
- Если маршрут сервиса изменился после выбора группы, прежнее подтверждение становится недействительным. Откройте актуальную карточку сервиса и начните подключение заново; повтор старой кнопки не вернёт сервис в старую группу.
- Перенос останавливается, пока повторное открытие обращения не завершилось или сообщение клиента из этого цикла ещё ожидает отправки либо имеет неизвестный исход. Дождитесь восстановления доставки и повторите подтверждение; так старый номер темы не будет использован в новой группе. Окончательная ошибка доставки после уведомления оператора остаётся видимой, но не блокирует перенос навсегда.
- Чтобы добавить сервисного бота в новую группу, откройте `/addbot` в личке управляющего бота и выберите **Создать новую группу**. Создайте группу с темами, добавьте управляющего бота и отправьте выданную команду `/connect …` в её General. После проверки добавьте сервисного бота в эту группу и завершите мастер. ID группы копировать и Cloudflare настраивать повторно не нужно. Для уже подключённой группы просто выберите её в списке. Подключение по токену и Managed Bots используют один защищённый маршрут; токен вводится только в личке управляющего бота.
- В карточке сервиса выберите основного и резервного оператора. Оператор должен состоять в списке действующих операторов и начать личный чат с управляющим ботом. Если ответственный недоступен, обращение назначается резервному или главному администратору.
- При выборе ответственного мастер проверяет текущий доступ управляющего бота к его личному чату. Если Telegram явно сообщает, что бот заблокирован, назначение не сохраняется, оператор помечается недоступным, а уже открытые обращения переходят резервному или главному администратору. После разблокировки оператору нужно отправить `/start`, затем `/available`. Проверка доступа в момент назначения не гарантирует доставку будущих уведомлений: их результат учитывается отдельно.
- Чтобы добавить оператора, попросите его отправить `/start` управляющему боту. После этого главный администратор откроет **Операторы** в своём меню и добавит человека из списка. Там же можно отозвать доступ. В карточке сервиса доступны интервалы напоминания и эскалации: 15/30, 30/60, 60/120 или 120/240 минут.
- Оператор открывает **Мои обращения** в личке управляющего бота. Список показывает сервис, имя клиента и время ожидания; 🔥 отмечает обращения старше первого порога напоминания. У главного администратора **Просроченные → Мои просроченные / Все просроченные** разделяет личную и общую очередь; у оператора в главном меню есть **Мои просроченные**. Из **Контроль и восстановление → Контроль ожидания** администратор может сразу перейти в общую очередь. В карточке можно взять обращение, снять назначение, отложить на час, отметить решённым или передать коллеге с внутренней заметкой. Повтор старой кнопки показывает текущее состояние и не выполняет действие второй раз. Личные напоминания отправляются после 30 и 60 минут ожидания по умолчанию; Cron проверяет их каждые пять минут.
- При выборе ответственного сервиса и передаче обращения показана текущая нагрузка каждого оператора: сколько обращений ждут ответа и сколько всего остаются в работе. Администратор видит эти числа также в списке операторов. Недоступный оператор отмечается при передаче; назначение ему по-прежнему проверяется перед сохранением.
- В теме обращения команда `/case` открывает карточку управляющего бота. Здесь можно взять обращение, снять назначение, отложить или отметить решённым; кнопка передачи открывает карточку этого же обращения в личке для ввода внутренней заметки. Кнопки из другой темы и устаревшие версии не меняют обращение. Если Telegram не подтвердил появление новой карточки, сначала осмотрите тему: бот не отправляет её повторно вслепую.
- **Все обращения** у главного администратора и **Мои обращения** у оператора показывают также активные темы в состоянии «Ждём клиента». Список разбит на страницы; из карточки такой темы можно изменить назначенного оператора, не меняя ответственного для всего сервиса.
- В карточке сервиса администратор запускает **Контрольный обмен**. Мастер открывает сервисного бота по ссылке, создаёт отдельную тестовую тему и предлагает подтвердить ответ из темы в личный чат. Статус «завершён» появляется только после обоих направлений; при неопределённом результате нужен осмотр тестовой темы и лички.
- В той же карточке доступны **Настройки сервиса**: приветствие, автоответ, реакции, цвет и эмодзи-иконка новых тем, а также часовой режим защиты AUTO/ON/OFF. После добавления нового бота кнопка **Скопировать сообщения** позволяет выбрать другой сервис, посмотреть его приветствие и подтверждение получения обращения и применить оба текста вместе с состоянием их отправки. Копирование меняет только нового бота; при изменении настроек после предпросмотра нужно подтвердить заново. Сохранённые ранее тексты и настройки читаются из тех же таблиц D1. Проверку реакций запускайте при подключении бота; оба направления включатся автоматически только после успешной проверки. В карточке сервиса есть проверка готовности. **Очереди**, **Проблемы доставки** и **Черновики** находятся в разделе **Очереди, доставка, черновики**; общий повтор доставки и состояние системы — в **Контроль и восстановление**; **План Cloudflare** и **Хранилище** — в **План и хранилище**. Пользователи, поиск и журнал действий доступны из главного меню Админушки, модерация и история — из карточки пользователя. Кнопки старого меню сервисного бота в General больше не используются.
- Тестовая тема не является обращением клиента. После успешного обмена сервисный бот пытается закрыть её автоматически; если Telegram отклонит закрытие, бот сообщит об этом в личку. Повторить закрытие можно командой `/close@example_manager_bot` в тестовой теме. В обычной теме эта же команда закрывает обращение через управляющего бота. Оператор также может нажать **Закрыть тему** в карточке обращения; в личной карточке есть и обратная кнопка **Открыть тему**.
- Экран **Контроль ожидания** показывает число обращений, превысивших первый порог без ответа, неясные исходы доставки, ошибки личных уведомлений по открытым обращениям, число недоступных операторов и карточки, у которых обновление ссылки после переноса ещё не подтверждено. Кнопка **Операторы** ведёт к списку, где недоступные операторы отмечены; после разблокировки бота оператору нужно отправить ему `/start`, затем `/available`. Ранее отправленные карточки не дублируются: управляющий бот обновляет их кнопки, а Cron безопасно повторяет обновление. Для конкретного сообщения оператора ответьте командой `/status` в его теме; кнопка обновления перечитает фактическое состояние из базы.
- Повтор одного и того же обновления Telegram не создаёт второе сообщение управляющего бота, если исход первой отправки неизвестен. В таком случае оператор может открыть новый экран отдельной командой или кнопкой. Завершённые уведомления по старым циклам очищаются порциями: отправленные и отменённые через 30 дней, неудачные и с неопределённым исходом через 180 дней. Записи текущего незавершённого цикла сохраняются для защиты от повторной отправки.
- В карточке сервиса экран **Повторная доставка** показывает сохранённые сообщения и позволяет запустить безопасное восстановление из базы. Если сервисный бот потерял доступ к группе, сообщение клиента остаётся в очереди; после возврата прав его можно повторить этим экраном либо дождаться Cron. Отправки с неясным результатом требуют ручной проверки и автоматически не повторяются.

Для проверки маршрута используйте отдельного тестового сервисного бота, группу с темами и два своих аккаунта: клиентский и операторский. Отправьте обычный текст от «клиента», проверьте, что он попал только в выбранную группу, ответьте в новой теме и проверьте получение ответа. Отдельно проверьте повтор после закрытия и уведомление ответственному. Не используйте для этого реального клиента.

## Откат и восстановление

До первого переноса сервиса можно вернуть предыдущий выпуск основного Worker из сохранённого артефакта. Новые таблицы D1 оставьте на месте: применённые миграции назад не запускайте. Уже работающие сервисные боты продолжат использовать прежнюю общую группу. Проверьте их webhook и обмен в обе стороны после возврата выпуска.

После переноса сервиса в отдельную группу **не публикуйте старый Worker напрямую**: он использует общую `SUPPORT_GROUP_ID` и может спутать темы. Если отказал только управляющий бот, оставьте текущий Worker и маршруты сервисов; клиентская доставка продолжит работать. Исправьте токен, права или webhook управляющего бота и повторите контрольный обмен.

Если нужно вернуть сам сервис в прежнюю группу, используйте мастер переноса в управляющем боте. Сначала разберите незавершённые и неопределённые доставки, затем проверьте новый маршрут, ответ из старой темы и ответ клиенту. При повреждении базы восстановление из резервной копии требует сверки сообщений, появившихся после копии; автоматического безопасного отката D1 для них нет.
