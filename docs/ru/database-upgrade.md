# Создание и обновление баз данных

Новая база получает начальную схему и последующие обновления:

- `migrations/0023_initial_schema.sql` — база бота `SUPPORT_DB`;
- `migrations/0024_bot_messages_and_navigation.sql` — настраиваемые сообщения и меню управления;
- `migrations/0025_bot_setup_notices.sql` — напоминания о настройке сообщений нового бота;
- `migrations/0026_manual_delivery_runs.sql` — ручные запуски повторной доставки и индексы очередей;
- `migrations/0027_verification_notice_status.sql` — ID сообщения капчи и восстановление её видимого статуса;
- `migrations/0028_user_access_alerts.sql` — очередь уведомлений об ограничении доступа пользователей;
- `migrations/0029_bot_registration.sql` — подключения ботов через Telegram и зашифрованные учётные данные;
- `migrations/0030_reaction_checks.sql` — раздельная проверка и включение направлений реакций;
- `migrations/0031_operator_workspace.sql`–`0035_workspace_invariants.sql` — рабочие экраны оператора, состояния обращений и настройки; [порядок обновления](retention.md);
- `migrations/0036_operator_initiated_auto_reply.sql` — подавление автоответа в разговоре, который первым начал оператор; добавляет триггеры, совместимые с текущим Worker;
- `migrations/0037_service_groups.sql`–`0056_statistics_review.sql` — привязка сервисов к группам, управляющий бот, перенос статических ботов, поиск и навигация рабочих экранов; [порядок включения](manager-bot.md);
- `monitor/migrations/0005_initial_schema.sql`–`0007_statistics_runtime.sql` — отдельная база мониторинга `MONITOR_DB`.

Это две разные базы, поэтому объединять их в одну не нужно. Начальные схемы объединяют старую цепочку миграций и после выпуска не меняются. Новые функции получают небольшие обновления для уже работающих баз. Отдельный `monitor/schema.sql` больше не нужен.

## Новая, пустая база

После создания D1 и заполнения `database_id` в соответствующем `wrangler.toml` выполните из корня проекта:

```powershell
npx wrangler d1 migrations apply telegram-support --remote --config wrangler.toml
npx wrangler d1 migrations apply support-monitor --remote --config monitor/wrangler.toml
```

Команды применят только ещё не выполненные файлы: для новой основной базы — `0023`–`0056`, для мониторинга — `0005`–`0007`. Повторный запуск пропустит уже применённые файлы. Используйте именно `migrations apply`: прямой импорт через `d1 execute --file` не зарегистрирует её в журнале Wrangler.

## Обновление базы, уже созданной по схеме 0023

Начните с резервной копии и проверки локальных миграций командой `node scripts/validate-d1-migrations.mjs`. Затем примените все недостающие миграции перед публикацией Worker. Если `BOT_REGISTRY_KEY` уже установлен, не заменяйте его. Для подключения Админушки следуйте [отдельной инструкции](manager-bot.md).

Выполните обычный `d1 migrations apply telegram-support --remote --config wrangler.toml`, затем настройте ключ и разверните Worker в порядке из инструкции. Будут применены отсутствующие обновления `0024`–`0056`; уже установленные файлы пропускаются. Существующие диалоги, связи сообщений, блокировки и настройки сохраняются. Открытые обращения не получают неожиданный автоответ после обновления. Приветствия и автоответы изначально выключены. Настройка текстов: **Админушка → Управление ботами поддержки → сервис → Настройки сервиса**. Для включения управляющего бота выполните [отдельные шаги установки](manager-bot.md).

## Существующая база со старыми миграциями

Для неё нужен однократный переход. Новый SQL создания таблиц нельзя запускать поверх существующих таблиц. Не удаляйте базу и не очищайте `d1_migrations`.

1. Проверьте, что имена и `database_id` в обоих конфигурационных файлах относятся к нужным базам. Сделайте резервный экспорт перед обновлением:

   ```powershell
   npx wrangler d1 export telegram-support --remote --config wrangler.toml --output support-before-schema-upgrade.sql
   npx wrangler d1 export support-monitor --remote --config monitor/wrangler.toml --output monitor-before-schema-upgrade.sql
   ```

   Сохраните экспорты отдельно от Git: они содержат данные. Для повторного экспорта выберите новое имя файла.

2. Подготовьте локальные файлы перехода:

   ```powershell
   node scripts/prepare-database-upgrade.mjs support
   node scripts/prepare-database-upgrade.mjs monitor
   ```

   Нужен Node.js 22.13+ с `node:sqlite`, как для тестов проекта. Скрипт только создаёт временную папку и копию конфигурации; к Cloudflare он не обращается. Для каждой базы он напечатает готовую команду Wrangler с путём к этой папке. Если после подготовки меняли конфигурацию, подготовьте файлы заново.

3. В окно обслуживания приостановите обработку сообщений и фоновые задания обоих Worker. Выполните напечатанные команды, проверив базу в подтверждении Wrangler. Временную конфигурацию используйте только для перехода базы, не для deploy.

   Wrangler проверит старый журнал, применит только недостающие старые шаги и проверит итоговую схему. Последний шаг зарегистрирует новую начальную схему как уже применённую, без пересоздания таблиц. Переписка, связи сообщений, баны и настройки сохраняются; преобразования старых служебных данных остаются такими же, как в первоначальных миграциях.

4. После успешного перехода вернитесь к обычным конфигурационным файлам. Проверка:

   ```powershell
   npx wrangler d1 migrations list telegram-support --remote --config wrangler.toml
   npx wrangler d1 migrations list support-monitor --remote --config monitor/wrangler.toml
   ```

   Начальная схема больше не должна числиться среди ожидающих применения. Примените последующие ожидающие обновления обычной командой `d1 migrations apply` с основной конфигурацией. Затем разверните Worker и возобновите работу по [инструкции включения функций](retention.md).

Если переход прервался, исправьте причину и повторите ту же команду: завершённые шаги пропускаются. Проверки отклоняют отсутствующий или непоследовательный старый журнал и несовместимую структуру. Не обходите ошибку удалением записей журнала. Для базы, импортированной вручную без журнала, требуется отдельная сверка; автоматический переход её не изменяет. Уже созданной по новой схеме базе переход не нужен.

## Зачем оставлен архив

`database/legacy-migrations.json` хранит прежние 26 шагов в одном файле исключительно для совместимости и тестов перехода. Wrangler при обычном запуске его не читает. Не редактируйте архив: имена и SQL должны совпадать с тем, что применялось раньше.

После выпуска новые изменения структуры потребуют новых небольших миграций: уже работающие базы должны получать обновления без потери данных. Применённые начальные схемы также не следует менять задним числом.

Проверки: `node scripts/validate-migrations.mjs` проверяет текущие схемы, `node scripts/validate-d1-migrations.mjs` применяет миграции на временных локальных базах через Wrangler; `node --test test/database-schema.test.js` сверяет их со старой цепочкой и проверяет переход со всех 26 прежних версий с сохранением данных.

Устройство журнала и команд описано в [документации миграций D1](https://developers.cloudflare.com/d1/reference/migrations/), экспорт — в [документации импорта и экспорта D1](https://developers.cloudflare.com/d1/best-practices/import-export-data/).
